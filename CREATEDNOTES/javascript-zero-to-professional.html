The roadmap

JavaScript is really four things layered on top of each other: a language (defined by the ECMAScript specification), a runtime that executes that language, a host environment (the browser, or Node.js) that adds APIs the language itself doesn't define, and the engineering practices that turn working code into maintainable software. Each level below builds the mental model you need for the next one — skipping ahead usually means guessing at concepts you'll have to unlearn later.

Language vs. platform, from day oneThroughout this course, code is labeled core JS when it's part of the ECMAScript language itself (works in any engine — a browser, Node.js, Deno) or platform API when it's provided by the host environment, like document, fetch, or localStorage. Confusing the two is one of the most common sources of confusion for self-taught developers.

What is JavaScript, and what is ECMAScript? concept

JavaScript is a programming language. ECMAScript is the specification — the written standard, maintained by a group called TC39 — that defines exactly how the language must behave. Every JavaScript engine (V8 in Chrome and Node.js, SpiderMonkey in Firefox, JavaScriptCore in Safari) is an independent implementation of that same specification.

This matters practically: when you read "ES2020" or "ES6", that's a yearly edition of the ECMAScript spec, not a separate language. New syntax you'll learn later — let, arrow functions, classes, async/await — are all ECMAScript features that engines implement over time. If a feature doesn't work, it's usually because the engine running your code is older than the spec edition that introduced it, not because "JavaScript" and "ECMAScript" disagree.

MENTAL MODEL
ECMAScript spec→implemented by→an engine (V8, SpiderMonkey…)→runs your JavaScript
Why the name "JavaScript" at all?It was created in 1995 at Netscape and given a name that borrowed Java's popularity for marketing reasons. Beyond syntax that superficially resembles C-family languages, JavaScript and Java are unrelated languages with different designers, semantics and use cases.
Exercise: spot the layer

For each item, decide: is it part of the ECMAScript language, or something else? Array.prototype.map · document.querySelector · async/await · Node's fs module.

Show answer

Array.prototype.map and async/await are core ECMAScript — they work identically in a browser tab and in Node.js with no HTML or filesystem involved. document.querySelector is a browser (DOM) API, not JavaScript itself — there is no document in Node.js. Node's fs module is a Node.js host API — it doesn't exist in a browser.

Engine, runtime, and host: browser vs. Node.js concept

An engine (like V8) only knows how to execute ECMAScript: variables, functions, objects, math, string manipulation. It has no idea what a web page or a file system is. A host environment embeds that engine and hands it extra objects to work with:

  • The browser embeds an engine and adds window, document, fetch, localStorage, and DOM events.
  • Node.js embeds the same V8 engine used in Chrome, but instead adds filesystem access, process, and module loading — with no document at all.

Together, engine + the extra objects a host provides + the scheduling machinery that drives asynchronous code is usually called the runtime. This is why "JavaScript can run anywhere" is true for the language, but a script written for the browser (using document) will crash immediately in Node.js, and vice versa.

Browser console
console.log(typeof window);     // "object"  — exists in the browser
console.log(typeof document);   // "object"  — exists in the browser
console.log(typeof process);    // "undefined" — this is a Node.js global
→Run this in Chrome/Firefox DevTools — process is undefined because that's a Node.js-only host object.
Common mistakeCopying a browser-focused tutorial's code into a Node.js script (or the reverse) and assuming "it's all JavaScript" means it will just work. The language is shared; the surrounding objects are not.
Running JavaScript: console, inline, and external scripts concept

There are three common places JavaScript executes while you're learning, and code in this course will always tell you which one it expects:

BROWSER CONSOLE

Open DevTools (F12 or right-click → Inspect → Console) and type code directly. Great for quick experiments; nothing is saved.

EXTERNAL SCRIPT FILE
index.html
<!doctype html>
<html>
  <body>
    <h1>Hello</h1>
    <script src="script.js" defer></script>
  </body>
</html>

The defer attribute tells the browser to download the script in the background but run it only after the HTML has finished parsing — the standard way to load scripts that touch the page's content.

INLINE SCRIPT
index.html
<script>
  console.log("Running directly inside the page");
</script>

Works, but mixes structure (HTML) with behavior (JavaScript) in one file — fine for a five-line demo, avoided in real projects.

Statements, expressions, and syntax concept

An expression is any piece of code that produces a value: 2 + 2, "hi".length, true. A statement is a complete instruction — it may contain expressions but doesn't itself produce a value you can use elsewhere: an if block, a loop, a variable declaration.

The practical test: can you put it on the right-hand side of an assignment? const x = (2 + 2) works — it's an expression. const x = (if (true) {}) is a syntax error — if is a statement, not a value-producing expression.

Browser Console
3 + 4;              // expression statement — evaluates to 7, value is discarded
const total = 3 + 4; // statement, containing the expression "3 + 4"
true ? "yes" : "no"; // the ternary IS an expression — it can be assigned

JavaScript statements typically end with a semicolon. The engine can often insert missing semicolons automatically (a behavior called Automatic Semicolon Insertion), which is why beginner code sometimes "works" without them — but ASI has sharp edges, covered in the exercise below, so this course writes semicolons explicitly.

PREDICT THE OUTPUT — semicolon insertion
function getValue() {
  return
    { value: 42 };
}

console.log(getValue());
Reveal answer

Output: undefined — not the object.

Automatic Semicolon Insertion treats a line break immediately after return as the end of the statement, so the engine actually runs return; followed by an unreachable object literal. This is the single most-cited real-world ASI bug. The fix: always put the returned value on the same line as return, or wrap it in parentheses.

Comments, formatting, and "strict mode" concept
script.js
// A single-line comment — ignored by the engine

/*
  A block comment.
  Useful for longer explanations.
*/

"use strict";
// Enables strict mode for the rest of this file (or function).

Strict mode is an opt-in mode that makes JavaScript stricter about mistakes it would otherwise silently allow — for example, assigning to an undeclared variable throws an error instead of quietly creating a global one. Code inside ES modules and inside classes is automatically strict; plain scripts are not, unless you add "use strict"; at the top.

script.js
"use strict";
mistypedVarName = 5;
// ReferenceError: mistypedVarName is not defined

// Without "use strict", the line above would silently
// create a global variable instead of failing loudly.

Declaring variables: let, const, varconcept

A variable is a named binding to a value. JavaScript has three declaration keywords, and they are not interchangeable style choices — they have different scoping rules.

script.js
const name = "Ada";     // cannot be reassigned — the default choice
let age = 30;           // can be reassigned — use when the value will change
age = 31;               // OK

var oldStyle = "avoid"; // function-scoped, hoisted oddly — legacy only

name = "Grace";         // TypeError: Assignment to constant variable.
→TypeError: Assignment to constant variable.

Default to const. Reach for let only when you know the binding needs to change (a loop counter, an accumulator). Reserve var for reading legacy code — it's function-scoped rather than block-scoped, meaning it leaks out of if/for blocks in ways that cause real bugs, and it's hoisted with an initial value of undefined rather than being genuinely unreachable before declaration.

const doesn't mean "immutable"It means the binding can't be reassigned — the variable name can't be pointed at a different value. If that value is an object or array, its contents can still change: const arr = [1]; arr.push(2); is perfectly legal.
The eight types, and typeofconcept

JavaScript has seven primitive types plus object. Primitives are immutable and compared by value; objects are compared by reference (covered fully in Level 04).

Common mistaketypeof null === "object" is not a design choice you should imitate reasoning from — it's a bug preserved for backward compatibility since JavaScript's first release. To check for null specifically, compare directly: value === null.

undefined vs. null: undefined means "nothing has been assigned yet" (the engine's default). null means "a developer explicitly assigned no value." Use null when you want to represent absence on purpose.

Type coercion, truthy & falsyconcept

Coercion is JavaScript converting a value from one type to another. Explicit coercion is a conversion you write on purpose (String(42), Number("42"), Boolean(0)). Implicit coercion happens automatically when an operator receives operands of mismatched types.

Exactly six values are falsy — they become false when coerced to boolean: false, 0, -0, "", null, undefined, and NaN. Every other value is truthy, including "0" (a non-empty string), [], and {}.

Equality: == vs ===concept

=== ("strict equality") compares type and value with no coercion. == ("loose equality") coerces the operands to a matching type first, following rules that are easy to misremember. The professional convention is: always use === and !==, with exactly one common exception.

script.js
value === null            // strict check for null only
value == null             // true for BOTH null and undefined — the one
                           // widely-accepted, intentional use of `==`

'5' === 5   // false — different types, no coercion
'5' == 5    // true  — '5' is coerced to a number first
Operators: arithmetic, logical, ternary, nullish coalescing, optional chainingconcept
script.js
// Arithmetic
10 % 3;          // 1  — remainder
2 ** 8;          // 256 — exponent

// Logical (short-circuiting)
false && expensiveCall();  // expensiveCall() never runs
true  || expensiveCall();  // expensiveCall() never runs

// Ternary — an expression form of if/else
const label = age >= 18 ? "adult" : "minor";

// Nullish coalescing — fallback ONLY for null/undefined
const port = config.port ?? 3000;
// (?? is different from ||, which also falls back on 0, "", false)

// Optional chaining — stop instead of throwing on a missing link
const city = user?.address?.city;  // undefined, no TypeError,
                                    // if user or address is null/undefined
Common mistakeconfig.retries || 5 silently overrides an intentional 0 with 5, because 0 is falsy. When zero (or an empty string, or false) is a valid value you want to keep, use ?? instead of ||.
Branching: if / else / switchconcept
script.js
function describe(temp) {
  if (temp < 0) {
    return "freezing";
  } else if (temp < 15) {
    return "cold";
  } else if (temp < 25) {
    return "mild";
  } else {
    return "hot";
  }
}

function describeSwitch(day) {
  switch (day) {
    case "Sat":
    case "Sun":
      return "weekend";
    default:
      return "weekday";
  }
}

Prefer switch when comparing one value against many exact matches (it also supports fall-through, shown above with "Sat"/"Sun" sharing a branch). Prefer if/else if for ranges or unrelated conditions. Always include a default case, and always return or break — forgetting break is a classic bug that lets execution "fall through" into the next case unintentionally.

Loops: for, while, do...while, break, continueconcept
script.js
for (let i = 0; i < 3; i++) {
  console.log(i); // 0, 1, 2
}

let n = 3;
while (n > 0) {
  console.log(n);
  n--;
}

let attempts = 0;
do {
  attempts++;             // runs at least once, even if the
} while (attempts < 0);   // condition is false from the start

for (let i = 0; i < 10; i++) {
  if (i === 3) continue;  // skip this iteration
  if (i === 6) break;     // stop the loop entirely
  console.log(i);         // 0, 1, 2, 4, 5
}

Use for when you know how many iterations you need (often tied to an array's length — though Level 04 introduces cleaner ways to iterate arrays). Use while when the stopping condition depends on something that changes unpredictably. do...while is rare, reserved for "run once no matter what."

PREDICT THE OUTPUT — coercion in conditionals
const values = [0, "", "0", null, undefined, NaN, [], {}];

for (const v of values) {
  console.log(v, Boolean(v));
}
Reveal answer

0 false, "" false, "0" true, null false, undefined false, NaN false, [] true, {} true.

The string "0" and the empty array/object are the values beginners most often mispredict — they "look empty" but are not one of the six falsy values, so they coerce to true.

LEVEL 03

Functions, Scope & Closures

Functions are how JavaScript packages behavior for reuse. Scope determines what a piece of code is allowed to see. Closures — where those two ideas intersect — are the single concept beginners find hardest, and the one professional code leans on constantly.

Three ways to write a functionconcept
script.js
// 1. Function declaration — hoisted: usable before its definition
function add(a, b) {
  return a + b;
}

// 2. Function expression — a function assigned to a variable,
//    NOT hoisted in a usable way (the variable is, the value isn't)
const subtract = function (a, b) {
  return a - b;
};

// 3. Arrow function — shorter syntax, and no own `this` (see Level 05)
const multiply = (a, b) => a * b;          // implicit return
const square = x => x * x;                  // single param, no parens needed
const logAndAdd = (a, b) => {               // block body needs explicit return
  console.log("adding", a, b);
  return a + b;
};

Function declarations are hoisted with their full body, so they can be called earlier in the file than they're written. Function expressions (including arrow functions) are only usable after the line that defines them runs — calling one earlier throws exactly the kind of error you'd expect from const/let hoisting.

Common mistakeArrow functions are not simply "shorter functions." They deliberately don't bind their own this, don't have an arguments object, and can't be used as constructors with new. Reach for a regular function when you need any of those; arrow functions are usually right for short callbacks.
Parameters: default, rest, and spreadconcept
script.js
// Default parameter — used only when the argument is undefined
function greet(name = "friend") {
  return `Hello, ${name}!`;
}
greet();          // "Hello, friend!"
greet(undefined); // "Hello, friend!"
greet(null);      // "Hello, null!" — null is a real value, default is skipped

// Rest parameter — gathers remaining arguments into a real array
function sum(...numbers) {
  return numbers.reduce((total, n) => total + n, 0);
}
sum(1, 2, 3, 4); // 10

// Spread — the opposite direction: expand an array into arguments
const nums = [4, 9, 16];
Math.max(...nums); // 16

Rest and spread use identical ... syntax but do opposite jobs depending on position: in a parameter list, ... collects values; in a function call or array/object literal, ... expands them. Level 04 revisits spread for copying arrays and objects.

Callbacks and higher-order functionsconcept

Functions are values in JavaScript — they can be stored in variables, passed as arguments, and returned from other functions. A function that receives or returns another function is called a higher-order function; a function passed in to be called later is called a callback.

script.js
function processOrder(item, onComplete) {
  console.log(`Processing ${item}...`);
  onComplete(item);          // "onComplete" is a callback
}

processOrder("book", (item) => {
  console.log(`${item} shipped!`);
});
// Processing book...
// book shipped!

// A higher-order function that RETURNS a function:
function multiplyBy(factor) {
  return (n) => n * factor;
}
const double = multiplyBy(2);
double(5); // 10

This pattern is the foundation for array methods like map/filter (Level 04), DOM event handlers (Level 06), and Promises (Level 07) — all of them are, underneath, "pass a function in to be called later."

Scope: global, function, block, and lexical scopeconcept

Scope is the region of code where a variable name is visible. let/const are block-scoped — confined to the nearest { }. Lexical scope means that visibility is determined by where code is physically written, not by which function called it — an inner function can always see variables from the function(s) it's written inside of.

MENTAL MODEL

script.js
const level = "global";

function outer() {
  const level = "function"; // shadows the global one, inside outer()
  if (true) {
    const level = "block";  // shadows again, inside this { }
    console.log(level);     // "block"
  }
  console.log(level);       // "function" — the block's binding is gone
}

Closures: functions that rememberconcept

A closure is what you get when an inner function is created inside an outer function, and that inner function is used after the outer function has finished running — yet it can still read and update the outer function's variables. The variables aren't copied; the inner function keeps a live reference to the outer function's actual lexical environment, which is kept alive in memory specifically because something still references it.

MENTAL MODEL
outer function runs→creates local state→returns inner function→outer "finishes"→inner function keeps access
script.js
function makeCounter() {
  let count = 0;                 // private state — invisible from outside
  return function () {
    count += 1;
    return count;
  };
}

const counterA = makeCounter();
const counterB = makeCounter();  // an entirely separate closure

counterA(); // 1
counterA(); // 2
counterB(); // 1 — counterB has its own independent `count`
→Two calls to makeCounter() create two separate, isolated closures — proven live below.
LIVE DEMO — two independent closuresruns in this page

Common mistakeCreating closures inside a loop with var is a classic bug: all the closures end up sharing the single function-scoped var, so they all "remember" its final value. Using let fixes it, because let creates a fresh binding for every loop iteration.
PREDICT THE OUTPUT — var vs let in a loop
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log("var:", i), 0);
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log("let:", j), 0);
}
Reveal answer

Output: var: 3, var: 3, var: 3, then let: 0, let: 1, let: 2 (relative order between the two loops can vary, but the pattern within each is fixed).

All three var closures share one binding, which equals 3 by the time any callback actually runs. Each let iteration gets its own binding, so each closure captured a different value. This is a real, frequently-tested interview question because it exercises scope, closures, and the event loop (Level 07) all at once.

Recursionconcept

A recursive function calls itself, moving toward a base case — a condition that stops the recursion. Without one, you get infinite recursion, which throws RangeError: Maximum call stack size exceeded (the call stack is covered in depth in Level 06).

script.js
function factorial(n) {
  if (n <= 1) return 1;        // base case
  return n * factorial(n - 1); // recursive case, moving toward the base case
}
factorial(5); // 120

function countdown(n) {
  if (n < 0) return;           // base case
  console.log(n);
  countdown(n - 1);
}
countdown(3); // 3, 2, 1, 0

Recursion isn't automatically better than a loop — it's a better fit for problems that are naturally self-similar (tree traversal, nested data, divide-and-conquer algorithms). For simple counting, a loop is usually clearer and avoids call-stack growth entirely.

Arrays: creation, indexing, and mutationconcept
script.js
const fruits = ["apple", "banana", "cherry"];
fruits[0];          // "apple" — zero-indexed
fruits.length;      // 3
fruits[fruits.length - 1]; // "cherry" — last element

References vs. values: why copying objects is trickyconcept

Primitives (strings, numbers, booleans, etc.) are compared and copied by value — each variable gets its own independent copy. Objects and arrays are compared and copied by reference — a variable holding an object actually holds a pointer to a shared location in memory. Assigning it to another variable copies the pointer, not the object.

MENTAL MODEL
variable name→reference (pointer)→the actual object in memory
script.js

obj2.count = 10;
console.log(obj1.count);   // 10 — they were always the same object

console.log(obj1 === obj2);          // true  — same reference
console.log({ a: 1 } === { a: 1 });  // false — different objects, same shape

Inheritance: extends and superconcept
script.js

    this.name = name;
  }

    return `${this.name} makes a sound.`;
  }
}

  constructor(name, breed) {
    super(name);       // MUST run before using "this" — calls Animal's constructor
    this.breed = breed;
  }
  speak() {             // overrides Animal's speak()
    return `${this.name} barks. (${super.speak()})`;
    // super.speak() explicitly calls the PARENT's version too
  }
}

rex instanceof Animal; // true — Dog IS an Animal in the inheritance chain

Prototypes: what classes are built fromconcept

JavaScript's inheritance is fundamentally prototype-based, not class-based — class syntax (added in ES2015) is a cleaner way to write the same underlying mechanism that existed since the language's first version. Every object has an internal link to another object, its prototype. When you access a property, the engine checks the object itself first, then walks up the prototype chain until it finds the property or reaches the end (null).

MENTAL MODEL
rex→ prototype →Dog.prototype→ prototype →Animal.prototype→ prototype →Object.prototype→null

// This is why methods defined on a class are shared, not duplicated
// per instance — every Dog reads the SAME speak() off Dog.prototype.

The this keyword, properly explainedconcept

this is not fixed by where a function is defined — with one major exception (arrow functions) — it's determined by how the function is called. There are four calling patterns:

script.js
const obj = {
  name: "Widget",
  show() { console.log(this.name); },
};

// 1. Method call — "this" is the object before the dot
obj.show(); // "Widget"

// 2. Plain function call — "this" is undefined in strict mode
//    (or the global object in non-strict, sloppy mode)
const detached = obj.show;
detached(); // TypeError: Cannot read properties of undefined
            // because "this" is undefined, not "obj"

// 3. Constructor call with "new" — "this" is the new instance
function Point(x) { this.x = x; }
const p = new Point(5); // this === p

// 4. Explicit binding — call/apply/bind FORCE what "this" means
function greet() { return `Hi, ${this.name}`; }
greet.call({ name: "Zed" });     // "Hi, Zed" — calls immediately
greet.apply({ name: "Zed" });    // same as .call, args passed as an array
const bound = greet.bind({ name: "Zed" }); // returns a new function,
bound();                                    // permanently bound — "Hi, Zed"

// Arrow functions have NO "this" of their own — they use whatever
// "this" was in the surrounding scope when they were DEFINED.
const arrowObj = {
  name: "Widget",
  show: () => console.log(this?.name), // "this" here is NOT arrowObj
};
arrowObj.show(); // undefined — inherited the outer (module/global) this
Common mistakePassing a method as a callback strips its binding: button.addEventListener("click", obj.show) calls show as a plain function, losing obj as this. Fix with obj.show.bind(obj), or wrap it: () => obj.show().
PREDICT THE OUTPUT — this inside a regular vs. arrow method
const timer = {
  seconds: 0,
  startRegular() {
    setInterval(function () {
      this.seconds++;          // regular function — new "this" each call
      console.log(this.seconds);
    }, 1000);
  },
  startArrow() {
    setInterval(() => {
      this.seconds++;          // arrow — keeps startArrow's "this"
      console.log(this.seconds);
    }, 1000);
  },
};
Reveal answer

startRegular() logs NaN repeatedly (or throws, in strict mode) — the plain function passed to setInterval is called with this as the global object (or undefined), not timer. startArrow() correctly logs 1, 2, 3... because the arrow function captures this from startArrow's own method-call context, where this === timer. This is the single most common reason developers reach for arrow functions inside callbacks that need access to an object's this.

Pure functions and immutabilityconcept

A pure function always returns the same output for the same input, and causes no observable side effects (no mutating arguments, no touching the DOM, no network calls, no relying on outside mutable state). Pure functions are trivially predictable, testable in isolation (Level 08), and safe to run multiple times.

script.js
// Impure — mutates its argument, a side effect
function addItemImpure(cart, item) {
  cart.push(item);
  return cart;
}

// Pure — same inputs always produce the same new output,
// original is left completely untouched
function addItemPure(cart, item) {
  return [...cart, item];
}

Real applications can't be 100% pure — something has to render to the screen or save data eventually — but isolating side effects to a thin outer layer, while keeping the core logic pure, is a widely-used professional discipline that pays off directly in Level 08's testing section.

Parsing, execution contexts, and the call stackconcept

Before running anything, the engine parses your source text into a structure it can execute, checking for syntax errors along the way. Then it executes code inside execution contexts — one is created for the global scope, and a new one for every function call, holding that call's local variables and its own lexical environment (this is the actual mechanism behind the scope rules from Level 03).

Execution contexts are tracked on the call stack — a last-in-first-out structure. Calling a function pushes a new context on top; returning from it pops that context off.

CALL STACK — for a chain of three function calls
main()callsfirst()callssecond()callsthird()

Stack, top to bottom, while third() is running: third() → second() → first() → main(). Each returns and is popped in the reverse order it was pushed — which is exactly why a stack trace (read top-to-bottom in DevTools) shows the innermost failing call first, followed by everything that called it.

script.js
function third() { throw new Error("boom"); }
function second() { third(); }
function first() { second(); }
first();

// Uncaught Error: boom
//   at third   (script.js:1)
//   at second  (script.js:2)
//   at first   (script.js:3)
//   at script.js:4      ← read top-down: where it broke, then who called it

A function that calls itself (or a cycle of functions calling each other) without a base case keeps pushing new contexts until the stack's fixed size limit is hit, throwing RangeError: Maximum call stack size exceeded — the runtime consequence of the recursion mistake introduced in Level 03.

Memory: the heap and garbage collectionconcept

Primitive values usually live directly on the call stack, sized and short-lived. Objects, arrays, and functions are allocated in a separate, larger memory region called the heap — which is why a variable "holding" an object is really holding a reference (Level 04) into the heap. When no reachable reference to a heap object remains anywhere (not on the stack, not inside another reachable object, not in a live closure), the engine's garbage collector frees that memory automatically — you never call free() yourself in JavaScript.

Why this matters practicallyA closure (Level 03) keeps its outer variables alive precisely because the inner function is a reachable reference to them — this is also the reason long-lived closures that capture large objects, or event listeners that are never removed, are a common source of memory growth ("leaks") in long-running applications, covered further in Level 09.
The DOM: a browser API, not JavaScript itselfconcept

When the browser loads an HTML page, it parses that markup into a live, in-memory tree of objects called the Document Object Model (DOM). document is the browser's entry point into that tree — an object supplied by the host environment, not defined anywhere in the ECMAScript spec. This is why the exact same JavaScript array/object/function knowledge from Levels 01–05 works identically in Node.js, while document.querySelector(...) would immediately throw ReferenceError: document is not defined there.

Events and listenersconcept

An event is the browser's notification that something happened — a click, a keystroke, a form submission, a page finishing load. You react to events by attaching a listener function that the browser calls when the event fires, passing it an event object describing what happened.

script.js
button.addEventListener("click", (event) => {

  console.log(event.target);  // the exact element that was clicked
});

});

Why asynchronous code existsconcept

The JavaScript language executes one thing at a time on a single call stack — there's no built-in concept of two lines of your code running simultaneously. Yet a browser tab clearly does many things "at once": downloading a file, ticking a timer, waiting on the network, all while the page stays responsive to clicks. It can do this because slow operations (timers, network requests, file access) aren't handled by the JavaScript engine itself — they're delegated to the host environment (the browser or Node.js), which does the actual waiting outside of JavaScript and then hands your code a callback, a Promise resolution, or an event once the result is ready.

The earliest pattern for this was a plain callback passed to an operation:

script.js
console.log("A");
setTimeout(() => console.log("B — runs later"), 1000);
console.log("C");
// Logged order: A, C, B — the script does NOT pause at setTimeout.

Nesting several dependent async callbacks produces deeply indented, hard-to-follow code informally called "callback hell" — the exact problem Promises (next lesson) and async/await were introduced to solve.

The event loop: stack, host APIs, and two queuesconcept

Here is the mechanism, precisely: JavaScript execution itself is single-threaded (one call stack), but the host environment provides additional threads and facilities behind the scenes for things like timers and network I/O. When you call setTimeout, the timer itself is handled by the browser, not the JS engine; once it expires, the callback isn't run immediately — it's placed into a queue. The event loop is the mechanism that continuously checks: "is the call stack empty? If so, take the next queued callback and push it onto the stack to run."

There are two queues, and they are not equal priority:

  • Microtask queue — Promise .then/.catch/.finally callbacks, and queueMicrotask. Fully drained after every single stack-emptying, before the next macrotask runs.
  • Macrotask (task) queue — setTimeout, setInterval, DOM events, network callbacks. One macrotask runs per pass of the loop.

Promises: pending, fulfilled, rejectedconcept

A Promise is an object representing a value that isn't available yet, but will be — eventually resolved (fulfilled with a value) or rejected (failed with a reason). It exists in exactly one of three states at any time, and once it leaves pending, it can never change state again.

MENTAL MODEL
pending→fulfilled (has a value)
pending→rejected (has a reason)
script.js
function wait(ms) {
  return new Promise((resolve, reject) => {
    if (ms < 0) return reject(new Error("negative delay"));
    setTimeout(() => resolve(`waited ${ms}ms`), ms);
  });
}

wait(500)
  .then(result => {
    console.log(result);      // "waited 500ms"
    return wait(200);          // returning a Promise CHAINS it
  })
  .then(result => console.log(result)) // "waited 200ms"
  .catch(err => console.error("Failed:", err.message))
  .finally(() => console.log("Done, either way"));

Chaining works because .then() itself returns a new Promise — if the callback returns another Promise, the chain waits on it; if it returns a plain value, the next .then() receives that value directly. A single .catch() at the end of a chain catches a rejection from any earlier step.

async/await, and the Promise combinatorsconcept

async/await is syntax sugar over Promises — it doesn't replace them, and it doesn't make code synchronous. An async function always returns a Promise; await pauses that function (not the whole program) until the awaited Promise settles.

script.js
async function loadProfile() {
  try {
    const user = await wait(300).then(() => ({ name: "Aya" }));
    const posts = await wait(300).then(() => ["post1", "post2"]);
    return { user, posts };
  } catch (err) {
    console.error("loadProfile failed:", err.message);
    throw err;                     // re-throw if the caller should also know
  }
}

loadProfile().then(profile => console.log(profile));

Use try/catch around await exactly like synchronous error handling (Level 08 covers try/catch in full) — a rejected awaited Promise throws at the await line. When several independent async operations don't depend on each other, awaiting them one-by-one wastes time; the combinators below run them concurrently:

script.js
// Promise.all — waits for ALL; rejects immediately if ANY one rejects
const [a, b] = await Promise.all([wait(100), wait(200)]);

// Promise.allSettled — waits for ALL, never short-circuits;
// gives you each result's status individually
const results = await Promise.allSettled([wait(100), Promise.reject("x")]);
// [{status:"fulfilled", value:...}, {status:"rejected", reason:"x"}]

// Promise.race — settles as soon as the FIRST one settles (win or lose)
const first = await Promise.race([wait(100), wait(500)]);

// Promise.any — settles as soon as the FIRST one FULFILLS,
// ignoring rejections unless ALL of them reject
const firstSuccess = await Promise.any([Promise.reject("no"), wait(50)]);
Common mistakeAn async function whose Promise is never .catch()'d, or awaited inside a try/catch, produces an unhandled promise rejection — logged as a browser warning, and silently swallowed application state that can be very hard to trace back to its source.
Fetch & HTTPconcept

script.js — real fetch, run in your own project
async function getUser(id) {
  const response = await fetch(`https://api.example.com/users/${id}`);

  if (!response.ok) {
    // fetch does NOT reject on 404/500 — you must check .ok yourself!
    throw new Error(`Request failed: ${response.status}`);
  }

  return response.json();  // ALSO returns a Promise — parses the JSON body
}

async function createUser(name) {
  const response = await fetch("https://api.example.com/users", {

Same-origin policy & CORSconcept

An origin is the combination of scheme + host + port (https://example.com:443). The browser's same-origin policy blocks a page's JavaScript from reading responses from a different origin by default — a security boundary that has nothing to do with whether the request itself is "allowed" over the network; the request may well reach the server, but the browser refuses to hand the response back to your script.

CORS (Cross-Origin Resource Sharing) is the mechanism that relaxes that restriction: a server that wants to allow cross-origin JavaScript access responds with headers like Access-Control-Allow-Origin, and the browser checks them before releasing the response to your code. For non-trivial requests (custom headers, methods other than GET/POST with simple bodies), the browser first sends an automatic preflight OPTIONS request to ask permission.

CORS is a browser mechanism, not a server firewallA missing CORS header doesn't stop the server from processing the request (that already happened) — it stops the browser from letting your JavaScript read the response. Tools like curl, or requests from a backend server to another backend server, are entirely unaffected because CORS is enforced only by browsers, for browser-run JavaScript.

Node.js and npm, conceptuallyconcept

Node.js is a JavaScript runtime built on Chrome's V8 engine, designed to run outside the browser — for servers, build tools, and command-line scripts. It adds host APIs the browser doesn't have (fs for the filesystem, process for the running program's environment) and has none of the browser's (no document, no fetch-free network stack in older versions, no DOM).

Node.js historically used its own module system, CommonJS (require()/module.exports), predating ES modules. Modern Node.js supports both — CommonJS by default in .js files, and ES modules when a file ends in .mjs or the nearest package.json sets "type": "module".

npm (Node Package Manager) installs and manages third-party code. A project's package.json lists dependencies (needed to run) and devDependencies (needed only during development, like a test runner), plus custom scripts you can run with npm run <name>. A lockfile (package-lock.json) pins exact installed versions so a project behaves identically on every machine. Package versions typically follow semantic versioning (MAJOR.MINOR.PATCH) — a major bump signals breaking changes.

An error not caught anywhere propagates up the call stack, function by function, until either a try/catch handles it or it reaches the top and crashes the script (or, for a Promise, becomes an unhandled rejection — Level 07). Catch errors at the level where you can actually do something meaningful about them; catching too early (and swallowing the error silently) hides real bugs.

    Cross-Site Scripting (XSS)security

    XSS happens when an attacker gets their own JavaScript to run inside your page, in the context of a legitimate user's session — able to read cookies, make requests as that user, or manipulate the page they see. DOM-based XSS specifically originates from client-side JavaScript writing untrusted data into the page in a way the browser executes.

    Vulnerable pattern → safe pattern 
    // VULNERABLE — a URL parameter rendered straight into HTML

    CSRF, Content Security Policy, and prototype pollutionsecurity

    CSRF (Cross-Site Request Forgery) tricks a logged-in user's browser into submitting a request to a site they're authenticated with, from a different, malicious site — exploiting the fact that cookies are attached automatically. Modern defenses include the SameSite cookie attribute and server-issued anti-CSRF tokens; this is primarily addressed server-side, but front-end developers need to recognize the risk when designing state-changing GET requests (avoid them — GET should never mutate data) or forms.

    Content Security Policy (CSP) is a response header that tells the browser which sources of scripts, styles, and other resources are allowed to load and run on a page — a defense-in-depth layer that can prevent an injected <script> tag from executing even if an XSS bug exists elsewhere. This is exactly the mechanism this course's own hosting environment enforces on generated pages.

    Prototype pollution is a vulnerability where attacker-controlled input reaches a key like "__proto__" in an object-merging or deep-clone function, letting the attacker inject properties onto Object.prototype itself — silently affecting every object in the program. It's most often introduced by naive recursive merge utilities that don't guard against special key names.

    Supply-chain risk: npm dependenciessecurity

    A typical project depends on dozens of packages, each of which may depend on dozens more. Every one of those is code you didn't write, running with the same privileges as your own — a compromised or maliciously-updated dependency (or one of its own dependencies) can affect your application. Practical habits: keep dependencies updated deliberately rather than blindly, review what a new dependency actually does before adding it for a trivial task, use lockfiles so installs are reproducible, and pay attention to your package manager's built-in vulnerability audit output.

    Performance: unnecessary work, debounce & throttleconcept

    The most common front-end performance problem isn't an inefficient algorithm — it's doing expensive work far more often than necessary. Repeatedly querying/mutating the DOM inside a loop, or running a full search on every single keystroke, are classic culprits. Two related techniques fix the keystroke case:

    • Debounce — wait until the user has stopped triggering an event for a set delay, then run once. Ideal for search-as-you-type.
    • Throttle — run at most once per fixed interval, no matter how often the event fires. Ideal for scroll/resize handlers.
    script.js
    function debounce(fn, delay) {
  let timeoutId;
  return function (...args) {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => fn.apply(this, args), delay);
  };
}

    Read this unfamiliar module and answer five questionsexercise 
    let cache = new Map();

    Without running it: (1) What is the input and output of getUser? (2) What is the module-level state? (3) What is asynchronous, and what can throw? (4) What happens if getUser(5) is called twice in a row? (5) What's a realistic bug this module could hide if id can represent the SAME user with two different types, e.g. 5 vs "5"?

    Show answer

    (1) Input: a user id; output: a Promise resolving to a user object, or a rejected Promise/thrown error. (2) The cache Map, shared across every call into this module. (3) The fetch and .json() calls are asynchronous; a non-OK response or a network failure can throw/reject. (4) The second call returns instantly from the cache without a new network request. (5) Map keys are compared by strict equality with no type coercion — 5 and "5" are treated as different keys, so the same user could be fetched and cached twice under two different "identities," silently doubling network calls and risking stale duplicate data.
